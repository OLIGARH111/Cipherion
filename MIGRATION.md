# Cipherion — миграция и восстановление

2026-10-02. **Production ещё не мигрирован.** Этот этап добавляет безопасную основу для следующих изменений. PostgreSQL/object storage не подключены; ниже явно разделены реализованные инструменты и дальнейший план.

## Текущее хранение

`DATA_DIR/cipherion.sqlite` содержит SQLite БД, `DATA_DIR/media` — вложения, `DATA_DIR/stickers` — пользовательские стикеры и постеры. SQLite использует WAL. Копировать только файл активной БД обычным `cp` нельзя: свежие транзакции могут оставаться в WAL.

Работающий Render-сервис и его диск ещё не проинвентаризированы. Не перезапускать и не redeploy сервис ради установки backup-скрипта, если это может уничтожить текущее ephemeral-хранилище. Получить копию через доступ к работающему экземпляру или существующий экспорт; если такого доступа нет — остановить миграцию и сначала решить получение данных.

## Реализовано: миграция схемы 1

`server/migrations.js`:

1. Перед инициализацией существующей БД проверяет максимальную версию.
2. Для старой версии делает SQLite online backup и проверяет целостность. Ошибка backup прерывает startup.
3. Более новая версия БД отклоняется, чтобы старый код не работал с неизвестной схемой.
4. После прежней инициализации модулей транзакционно добавляет `schema_migrations`, таблицу fingerprints сообщений, admin audit и индексы.
5. Повторный startup не повторяет миграцию 1.

Старые CREATE/ALTER в модулях пока не перенесены в общий registry. Это не завершённая консолидация схемы. Миграция добавляет таблицы/индексы, не удаляет данные. Для новых будущих версий нужно увеличивать schemaVersion и добавлять отдельные шаги с тестом upgrade/rollback.

Автоматическая копия пишется в BACKUP_DIR либо DATA_DIR/backups. Она содержит только БД. Это локальная страховка, **не** внешнее резервное хранение и **не** копия медиа. До deploy необходим полный backup за пределами хранилища сервиса.

## Реализовано: полный backup

До команды включить maintenance на уровне маршрутизации и запретить записи, дождаться окончания запросов/загрузок, остановить фоновые записи. Скрипт не устанавливает maintenance самостоятельно: флаг подтверждает, что оператор действительно обеспечил отсутствие писателей. Не останавливать ephemeral-контейнер до извлечения данных.

Пример для доступного каталога исходных данных:

```bash
node scripts/backup.js create /path/to/current-data /path/to/separate-backups/rc-2026-10-02 --maintenance-confirmed
node scripts/backup.js verify /path/to/separate-backups/rc-2026-10-02
```

Родительский каталог назначения должен существовать; конечный каталог должен отсутствовать. Назначение внутри DATA_DIR запрещено. Существующая копия никогда не перезаписывается. В случае ошибки остаётся неполная папка: она не считается пригодным backup и не заменяет последнюю проверенную копию.

Скрипт использует SQLite backup API, сохраняет standalone БД без зависимости от WAL, копирует media/stickers, отклоняет symlink, задаёт закрытые права файлов, записывает manifest с количеством строк всех пользовательских таблиц и SHA-256 каждого файла. Verify проверяет полный набор файлов, хеши, integrity, foreign keys, размеры медиа и наличие активных пользовательских стикеров/постеров.

Копию нужно зашифровать и перенести в отдельное закрытое постоянное хранилище. Не загружать БД в GitHub и не отправлять её в чат. Manifest не заменяет подпись: у того, кто может менять и backup, и manifest, есть возможность подменить оба. Нужны отдельные права доступа/immutable retention.

## Реализовано и протестировано: восстановление SQLite

1. Проверить backup командой verify. Ошибка означает остановку восстановления.
2. Создать **новый** изолированный каталог, скопировать туда весь проверенный backup (не использовать единственную backup-копию как рабочую БД).
3. Ещё раз выполнить verify над копией.
4. Запустить совместимую версию приложения с DATA_DIR этого каталога и отдельным портом/доменом. Не настраивать production push/AI/billing в restore rehearsal.
5. Проверить `/health`, количества записей, вход, историю, права и скачивание файлов. Автотест release.test.js делает восстановление и проверяет реальные HTTP-запросы к восстановленной тестовой БД.
6. Только после проверки перевести трафик на восстановленное хранилище. Старое сохранить до окончания наблюдения.
7. Не включать одновременно два независимых writable источника: записи разойдутся.

При ошибке до переключения продолжить работу прежнего источника. После переключения нельзя просто возвращать старый снимок: новые записи будут потеряны. Сначала остановить записи, сохранить новый источник и перенести изменения либо выполнить forward fix.

## Не реализовано: переход на внешнюю БД и object storage

1. Подтвердить Render workspace и service → repo → branch → commit. Проверить реальный DATA_DIR, persistent disk, env и наличие всех файлов.
2. Получить и внешне сохранить полный backup; выполнить restore rehearsal.
3. Выбрать и подключить постоянную БД и закрытый object storage с понятными квотами/retention. Секреты передавать через env, не в код/чат. Не создавать платные ресурсы без согласованного бюджета.
4. Зафиксировать исходную схему всех таблиц/триггеров/индексов и исходные row counts. Таблицы создаются многими модулями, поэтому одного server/db.js недостаточно.
5. Создать версионированную целевую схему: пользователи/профили/верификация; сессии; контакты/blocks/privacy; чаты/members; messages/replies/forwarding/reactions/receipts; media; stories/views; VIP/promos/audit; AI; push/jobs; polls; stickers; family; cloud и прочие существующие сущности.
6. При выборе PostgreSQL адаптировать синхронные SQLite-вызовы, placeholders, PRAGMA, SQL-функции, upsert и триггеры. Сохранить атомарность message+event+notification job, выдачи VIP и лимита промокода. Не подменять драйвер без этих изменений.
7. Для объектов сохранить исходные логические ID, назначить уникальные object keys, перенести байты, сверить размер и SHA-256. Проверку прав выполнять до выдачи подписанного URL/стрима. Не делать bucket публичным.
8. Сделать идемпотентный импорт в пустую staging БД. Сверить количество строк каждой таблицы, наборы primary keys, уникальность username/client IDs, FK/ссылки, несколько полных сценариев пользователей и все объекты. Количество строк само по себе недостаточно.
9. Прогнать integration-тесты на целевом драйвере, конкурентные отправки, рестарты, rollback при частично неудавшемся импорте и реальные устройства/сети.
10. На cutover остановить записи и фоновые задания, дождаться активных запросов, снять финальную копию/дельту, повторить сравнение. Переключать production только после успеха.
11. Проверить сохранность после redeploy, настроить внешние backups/оповещения и отрепетировать восстановление новой БД.

## Предлагаемый backup-регламент — пока не включён

- Перед каждым потенциально опасным изменением — отдельная проверенная копия.
- Ежедневная копия БД и инвентаризация объектов; начальная цель RPO ≤ 24 ч.
- Предлагаемая retention: 7 ежедневных + 4 еженедельных копии при достаточной квоте.
- Контроль последнего успешного backup и уведомление о пропуске.
- Еженедельная проверка целостности; регулярный restore rehearsal. RTO определять по реальному измерению восстановления, не обещать заранее.

Расписание, внешнее хранение и production restore пока отсутствуют и блокируют выпуск.
